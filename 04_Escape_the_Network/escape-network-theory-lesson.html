A graph inside a 2D list

Another valid representation

An adjacency list stores just the neighbours of each node. For example, A has neighbours B with cost 5 and C with cost 1. An adjacency matrix reserves space for every possible pair; an adjacency list avoids storing all the absent edges.

Chapter 3 · Decide what to process next

Queues and stacks change the search

Search algorithms keep a collection of work still to do. This is the frontier. The removal rule controls the order of exploration.

Queue · first in, first out

Think of a queue for the ferry. The first arrival leaves first. Add at the rear; remove from the front.

A arrived first. A will be removed next.

Stack · last in, first out

Think of a stack of trays. The last tray added is the first removed. Push onto the top; pop from the top.

C was added last. C will be removed next.
Visited records prevent loops. If your graph contains A–B–D–C–A, blindly following neighbours could revisit A forever. Record discoveries or visits and avoid repeating them according to the algorithm’s rule.

A predecessor records which node led to another node. If predecessor[F] = E, predecessor[E] = D and predecessor[D] = C, follow the links backwards to reconstruct the route, then reverse it.

Chapter 4 · Breadth first search

BFS explores the nearest layers first

Breadth first search uses a queue. It explores every node one edge away before moving on to nodes two edges away. With a FIFO queue, BFS finds a path with the fewest edges. It does not use the weights to choose its path.

  1. Put the start in the queue and mark it discovered.
  2. Remove the front node. If it is the goal, reconstruct the path.
  3. Inspect its neighbours in alphabetical order. Mark each new neighbour discovered when enqueuing it, and record its predecessor.
  4. Repeat until the goal is found or the queue is empty.
Predict first: after A is expanded, the queue contains B then C. Which is removed next? Which locations will be discovered from it?
Why mark a node when it enters the queue?

Two frontier nodes may share a neighbour. Marking it on enqueue prevents duplicate queue entries and preserves the first predecessor, which gives a fewest-edge path.

Chapter 5 · Depth first search

DFS follows a branch, then backtracks

Depth first search follows a path as far as it can before returning to try another neighbour. It uses a stack, or recursion, where unfinished function calls form a call stack.

This animation uses recursive DFS. A node is marked visited on entry. Its neighbours are considered alphabetically. If the branch cannot reach the goal, the function returns to its caller: this is backtracking.

  1. Enter a node and record it as visited.
  2. If it is the goal, reconstruct the path.
  3. Visit the first unvisited neighbour. Finish exploring that branch before trying the next.
  4. If no unvisited neighbours remain, return to the previous call.
Watch D to C: C has no unvisited neighbour, so DFS returns to D and tries E. C is explored, but it is not part of the final A-to-F path.
Why can another DFS implementation return a different path?

Changing neighbour order changes which branch DFS tries first. An explicit stack reverses the order of popped items: pushing neighbours A then B makes B come out first. Neither recursive nor iterative DFS guarantees the fewest edges or lowest cost.

Chapter 6 · Weighted shortest paths

Dijkstra keeps improving the cheapest known route

Dijkstra’s algorithm finds a minimum-total-cost path when all edge costs are non-negative. It does not simply pick the cheapest next edge from the current node. It compares the total costs of routes from the start.

Tentative distance
The cheapest total cost from the start found so far. It may improve.
Infinity · ∞
No route to this node has been found yet.
Relax an edge
Try distance[current] + edge cost. If that total is cheaper, update the neighbour’s distance and predecessor.
Settled
The node’s minimum distance is final. Always settle the unsettled node with the lowest tentative distance next.
Example of relaxation: C has distance 1. C to D costs 2. The proposed distance to D is 1 + 2 = 3. If D’s old distance is ∞ or greater than 3, replace it with 3 and record C as its predecessor.

Initialise the start to 0 and everything else to ∞. After settling a node, inspect its edges. Stop when the goal is settled or when no unsettled node has a finite distance. We break equal-distance ties alphabetically.

Why are negative weights excluded?

A settled distance might become cheaper through a later negative-cost edge. That breaks the reasoning that lets Dijkstra finalise distances. Validate weights before using this algorithm.

Chapter 7 · Compare and investigate

Same map, different goals

Run all three searches on the same graph and query. Compare an actual route, its number of edges, its total travel cost and the number of nodes expanded.

AlgorithmRouteEdgesCostExpanded
Count consistently. A node is expanded when its neighbour list is examined. We check for the goal first, so the goal is not counted as expanded. Discovered, expanded and path nodes are different things.

Try the direct A–F edge: BFS prefers one edge costing 18. Dijkstra finds a four-edge route costing 6. Then isolate F and try A to F. Finally, set start = goal: a one-node route has zero edges, cost 0 and zero expansions.

Efficiency without misleading timings

For adjacency lists, BFS and DFS are O(V + E), where V is the number of nodes and E the number of edges. With an adjacency matrix they can inspect a whole row per expanded node, giving O(V²) in the worst case. Dijkstra using a linear minimum-distance search takes O(V² + E) with adjacency lists, or O(V²) with a matrix. A tiny graph’s runtime is usually too small to compare reliably; record meaningful operation counts.

Plan these functions before coding

  1. get_neighbours(node): return connected nodes and their costs in a consistent order.
  2. bfs(start, goal) and dfs(start, goal): maintain the frontier, visited records and predecessors.
  3. dijkstra(start, goal): maintain distances, predecessors and settled nodes.
  4. reconstruct_path(predecessors, start, goal): follow links backwards, then reverse the path.
  5. route_cost(path): add the weights of consecutive edges.
  6. run_query(): validate nodes, copy the graph and block both directions temporarily.

Test cases to take into the project

  • Normal route; start = goal; unknown node.
  • Cycles, a dead end and an unreachable exit.
  • An expensive direct connection; a valid zero-cost edge; rejected negative cost.
  • A blocked edge in both directions, followed by a fresh unblocked query.
Three questions before any search: What counts as a connection? Which node should be processed next? What records are needed to build the final route?
